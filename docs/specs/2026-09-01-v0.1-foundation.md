# Agent Teamworks V0.1 Foundation Spec

**Status:** Accepted

**Accepted source:** Project conversation, 2026-09-01

**Positioning:** Persistent multi-agent teams for real projects.

## Purpose

Agent Teamworks turns a repeatable multi-agent collaboration method into an open-source project that can be applied across long-running, outcome-oriented projects.

The method treats a team as durable project infrastructure. Roles keep stable responsibilities and shared context across work items. A concrete agent process may be replaced, but the logical role, its authority, history, and obligations continue through an explicit handoff.

## Goals

V0.1 must provide:

1. A project operating model for forming, running, evolving, and closing a multi-agent team.
2. A persistent-role model that separates a logical role from the agent currently bound to it.
3. Outcome- and dependency-based work decomposition routed into the established team.
4. Clear coordinator, role, handoff, review, verification, acceptance, and escalation protocols.
5. Machine-readable schemas for Team, Role, Work Item, Handoff, and Decision records.
6. A thin Codex Skill entry that activates the method without embedding the whole framework in one Skill.
7. A sanitized project example and forward-evaluation scenarios based on recurring collaboration failures.
8. An open-source contribution path that preserves decisions and delivery history through branches and pull requests.

## Non-goals

V0.1 will not provide:

- a dashboard, hosted service, or autonomous agent runtime;
- a complex command-line application;
- a fixed universal roster for every project;
- mandatory multi-agent overhead for small or one-off tasks;
- automatic authority for publishing, spending, credentials, destructive changes, or merge decisions;
- a claim that engineering verification equals user acceptance.

## Core semantics

### Team

A Team is a durable project-level collaboration unit with one mission, one coordinator role, an explicit roster, an authority boundary, and a lifecycle state.

### Role

A Role is a persistent responsibility and decision boundary. Its stable identity is independent of the agent instance currently performing it. Only one active binding may own a role at a time.

### Work item

A Work Item is the smallest independently observable outcome worth routing and tracking. Work is split by outcome, dependency, mutable ownership, and evidence needs—not by arbitrary agent count.

### Handoff

A Handoff transfers current state, evidence, open obligations, and authority between roles or between successive agent bindings of the same role. Replacement without a completed handoff is a continuity failure.

### Decision

A Decision records a consequential choice, its authority, rationale, evidence, state, and supersession history. Proposed decisions are never represented as approved truth.

## Operating invariants

1. The user may interact primarily with the coordinator; internal role activity must return to that coordination surface.
2. The roster is the source of active ownership. Duplicate active owners for one role are invalid.
3. The team should be the smallest stable roster justified by the project mission and risk.
4. New work is decomposed first, then routed to existing roles. A new role is created only for a durable responsibility gap.
5. Every consequential state transition leaves a durable record.
6. Agent replacement increments the role binding generation and requires a completed handoff.
7. Implementers cannot approve their own outcome. Review depth must be proportional to a concrete risk or acceptance need.
8. Engineering verification and user acceptance remain separate states.
9. The agent may own routine branch, commit, push, and pull-request mechanics; merge remains explicitly authorized.
10. A team ends only through an explicit paused or dissolved lifecycle transition with remaining obligations recorded.

## Authority boundary

The framework supports local, reversible collaboration by default. It does not grant authority for consequential external actions. User or designated-owner approval remains required for publication, money, credentials, permissions, privacy-sensitive operations, destructive changes, acceptance decisions, and repository merge when applicable.

## Acceptance criteria

V0.1 is engineering-ready for review when:

- all five schemas are valid JSON Schema documents and the example records validate against them;
- the operating model covers formation, routing, execution, continuity, acceptance, and dissolution;
- the Codex Skill passes the bundled Skill validator;
- the example contains no private repository state, credentials, personal data, or unverifiable completion claim;
- evaluation cases cover duplicate roles, lost reporting, repeated review, invalid acceptance gates, agent replacement, and task-driven decomposition;
- repository checks run in CI and the feature branch is submitted through a pull request.

User acceptance remains pending until the project owner reviews and approves the pull request.
